# ORBIT Personal Context API V1 — 20 Read-Only Tools

**Status**: Implemented on feature branch; awaiting automated tests, hosted-development authentication tests, and integration. Not deployed.
**Base URL**: `/api/orbit/context`
**Purpose**: Answer natural-language questions using authenticated POS user data. These are owner-scoped **read-only** tools; they do not generate AI analysis, mutate source records, or hold a separate ORBIT personal database.

## Authentication, identity and sharing

- PROD and hosted-dev: existing Supabase ES256 JWT required for `/api/**`. Never send a userId in query, URL or JSON body. Every existing domain service reads the authenticated owner from `CurrentUserProvider`.
- Local dev uses a fixed dev user by existing project policy. Do **not** expose an unauthenticated local dev server to the Internet.
- ChatGPT connection needs an independently configured authenticated tool/connector. Publishing an API route does **not** automatically make it invokable from a chat.
- A Bearer token must never be pasted into a chat, report or GitHub issue. Do not add service-role database credentials or unrestricted database dumps.
- All responses are personal; treat as sensitive. Scrub body, query parameters, Bearer headers and source facts from access/debug logs, telemetry and support artifacts. Enforce TLS and avoid public caches (`Cache-Control: private, no-store` on ORBIT responses as a follow-up HTTP filter or configuration requirement).
- No frontend changes, migrations, domain writes, scheduled tasks, extra third-party APIs, or new database required for V1.

## Shared request conventions

- Unless stated otherwise, `from` and `to` are ISO `YYYY-MM-DD` inclusive in `Asia/Seoul`. Omit both for the last 14 local calendar days including today.
- Both dates required if either is supplied; bounded **1–31 days**. Historical facts cannot specify a future `to` date. The calendar/planning routes accept dates from 365 days ago through 31 days ahead and default to today through day 14 when both dates are omitted.
- A malformed or unbounded request returns HTTP 400. Missing source data is **not zero**, **not failure**, and **not evidence of compliance**.
- Pagination: `limit` defaults to 50 (1–100), `offset` defaults to 0 (0–10,000). Total is the matched-record count, not the page size. No open-ended unbounded API result for individual records.
- New context responses include `schemaVersion:1`, `context`, `timezone:Asia/Seoul`, `generatedAt`, `data`, and route-specific metadata.
- Two pre-existing SLEEP endpoints and the earlier DIET measurement endpoint have their **existing** JSON contracts; do not incorrectly claim all 20 return the same envelope.
- `date` uses ISO `YYYY-MM-DD`; `month` uses ISO `YYYY-MM`.
- No medical diagnosis, financial advice, causal attribution or fabricated record values are generated by the backend. ChatGPT should distinguish observation, arithmetic, interpretation and missing information.

## Route catalog

| # | GET endpoint suffix | Parameters | Data and source semantics |
|---|---|---|---|
| 01 | `get_sleep_context` | timezone (default Asia/Seoul) | Existing SLEEP context, recovery/measurement attribution governed by canonical SleepService |
| 02 | `get_recovery_context` | timezone (default Asia/Seoul) | Existing SleepRecoveryAdapter projection; do not infer a clinical diagnosis |
| 03 | `get_diet_context` | from, to (default 14 days, max 31) | Canonical diet_measurements: weight, glucose, bloodKetone, breathKetone; chronological readings plus first/last/change/average and sample counts |
| 04 | `get_diet_daily_context` | from, to | diet_days legacy daily fields including measurements and fasting hours; recorded days only |
| 05 | `get_diet_progress_context` | from, to | DIET checklist items, explicit checks, goals, challenges, period milestones and item archive intervals |
| 06 | `get_calendar_context` | from, to | Canonical CalendarRangeResponse preserving planned vs actual distinctions |
| 07 | `get_work_records_context` | from, to | Dated work records with work-time and supplemental-time entries; attendance/score source facts |
| 08 | `get_checklist_catalog_context` | none | Checklist SYS identities, areas, item definitions, start dates and archive intervals |
| 09 | `get_checklist_records_context` | from, to | Explicit checklist daily state facts; no record does not mean FAIL |
| 10 | `get_workflow_projects_context` | status?, limit, offset | Projects with goal, lifecycle/status and schedule; explicit pagination of aggregate catalog |
| 11 | `get_workflow_tasks_context` | status?, limit, offset | Tasks with priorities, deadlines, next steps, status and waiting context; preserve dueDate vs deadlineDate |
| 12 | `get_workflow_day_context` | date? (default today) | Workpad day blocks, hierarchy, task links, checked flags and revision |
| 13 | `get_workflow_plan_context` | from, to | Existing plan-day assignments; intention, **not** completed work |
| 14 | `get_workflow_waiting_context` | none | Current waiting and ready-to-check tasks from workflow projection |
| 15 | `get_money_overview_context` | from, to | Existing MONEY overview calculations. Never double-count transfers, refunds or debt principal as consumption |
| 16 | `get_money_transactions_context` | from, to, limit, offset | Paged MONEY transactions: amount/currency, type, meaningState, category, refund/merge linkage, evidence count; source payloads excluded |
| 17 | `get_money_accounts_context` | none | Account name, role, asset/statistics flags, fund group and calculated balance/provenance; no account reference or base64 image |
| 18 | `get_money_loans_context` | none | Existing canonical loan metadata, remaining principal, rate, schedules and link status; **not** an invented repayment schedule |
| 19 | `get_money_savings_context` | from, to, currency? (default KRW), limit, offset | Existing savings read model with transfer items, gross withdrawals, net and analytics availability |
| 20 | `get_money_earnings_context` | month? (default current) | Work-shift earnings calendar, expected vs confirmed vs received pay, daily and weekly allowance policies; at most 3 months future |

## Sample requests

```http
GET /api/orbit/context/get_diet_context?from=2026-10-19&to=2026-11-01
GET /api/orbit/context/get_workflow_tasks_context?status=WAITING&limit=30&offset=0
GET /api/orbit/context/get_money_transactions_context?from=2026-10-20&to=2026-11-01&limit=50
GET /api/orbit/context/get_money_earnings_context?month=2026-10
Authorization: Bearer <short-lived user JWT>
```

## Required validation before merge or deployment

1. `cd backend && ./gradlew test --tests com.kafka.backend.orbit.DietContextServiceTest --tests com.kafka.backend.orbit.OrbitReadServiceTest`
2. Compile and run nearby affected integration tests for DIET, Workflow, Money, Calendar, Checklist and Work Record services.
3. Confirm exactly 20 unique GET route mappings and no write mapping exposed under `/api/orbit/context`.
4. Hosted-dev: verify valid JWT 200, missing/expired JWT 401, and cross-owner 404/empty data with synthetic users.
5. Check invalid date/order, >31-day requests, future date, 101-record page limit and huge offset return bounded results/errors.
6. Test genuine empty periods and unknown/missing values; never convert null into zero.
7. Compare ORBIT JSON with original POS screens/endpoints for a **synthetic** period, including money financial semantics and weekly earnings.
8. Verify no secret leaks, raw notification payloads, account refs or base64 images in returned data.
9. Verify cache headers and sensitive request/response logging controls before external connector exposure.
10. Do not call this complete until hosted-dev and PROD smoke have passed with intended deployment authorization.
