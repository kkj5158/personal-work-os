## 구조와 데이터 보존

- WORKPAD 기존 모델은 블록 ID/parentId/형제 order이며, 링크의 실제 대상은 `metadata.wikiLinks.noteId`다. 노트 제목 문자열로 기존 ID를 대체하지 않았다.
- 노트의 기존 `journal_notes.content` Markdown 저장 경로를 유지한다. 버전 표식은 본문 뒤 주석에 블록 ID·계층·메타데이터·길이를 보존하며, 사용자 본문은 한 번만 저장한다. 신규 테이블·컬럼·Flyway 파일·운영 일괄 변환은 없다.
- 기존 Markdown은 열기만 해서는 저장하지 않는다. 처음 편집할 때 지원되는 제목/목록/체크/이미지를 기존 WORKPAD 블록으로 저장한다. 알 수 없는 문법은 TEXT 원문으로 유지한다. 기존 ID·노트 본문·이미지 참조를 삭제하는 변환은 하지 않았다.
- WORKPAD가 원래 제공하지 않던 Markdown 표/코드펜스/HTML/일부 인라인 문법은 원문을 보존한다. 이 작업에서 별도 rich renderer를 추가하지 않았으므로 이전 NOTE SYS의 일부 표시와는 다를 수 있다.
- malformed/future-version 형식은 원문을 유지하고 저장을 차단한다. Workspace rename은 기존 alias/reservation API를 이용하고, 그 성공 버전으로 본문을 저장한다.
- 백링크 목록은 50개, 문맥은 100개 단위로 추가 조회한다. 문맥은 기존 최대 5000블록인 해당 날짜만 읽고 parentId를 따라 추출한다. 날짜별 전체 문서를 언급마다 미리 조회하지 않는다.
- 소유자/노트/날짜/블록 참조를 검증한 뒤 문맥을 반환한다. 새 공유 권한이나 다른 사용자의 조회 범위를 만들지 않았다.
- 영속 계약: `docs/contracts/workpad-linked-notes.md`.

## 실패 이력과 실제 제한

초기 구현의 Chrome 중첩 contenteditable 커서 재설정과 문서 간 Add-block 선택 범위 잔류를 실제 브라우저에서 발견해 수정했다. 해당 실패 실행을 최종 PASS로 합산하지 않았다.

운영 후보 최초 병렬 QA는 frontend 포트 선점으로 실패했다. 다른 실행의 웹 서버는 종료하지 않았고, 해당 소유 DB/프로세스 정리 후 순차 재실행한 최종 후보가 PASS했다. 재사용 QA runner에는 시작 직전 포트 재확인과 커밋 변경 검사를 보강했다.

Chrome 문서가 hidden이 된 상태의 actionability timeout도 있었다. 기존 TEAM KAFKA 프로세스와 반환 native window ID를 대조해 기존 창만 복원한 뒤, visible 상태에서 정상 Playwright click/keyboard 검증이 통과했다. 개인 프로필·재시작·새 debug port·무관한 Tab Group 변경은 없었다.

미수행:

- 실제 OS 한글 IME 후보 선택 UI. 한국어 직접 입력과 기존 composition-aware 코드/테스트는 확인했다.
- 50/100 페이지 제한과 전체 접근성은 서버 자동 테스트로 확인했지만, 대규모 히스토리를 브라우저에서 끝까지 넘기는 시나리오는 실행하지 않았다.
- hosted DEV 변경 기능 및 PROD smoke. 승인 검토 차단으로 실제 배포가 이루어지지 않았다.
- 운영 데이터의 수동 변경·비교·복원. 운영 쓰기는 0이다.

## 인계: 승인 후 남은 작업

1. remote `dev`/`prod`와 위 SHA, Railway staged diff 및 다른 배포 작업 유무를 다시 확인하고 release lock을 획득한다.
2. DEV의 두 서비스 source pin 배포를 실행한다. 성공 deployment metadata가 `964ee731...`인지 확인하고 health와 실제 인증 DEV 화면의 변경 기능을 검증한다.
3. PROD 전용 후보의 두 서비스 배포를 실행한다. 성공 metadata가 `9fadeb8...`인지 확인하고 운영 인증/WORKPAD 읽기·링크/편집기 UI를 집중 smoke한다. 운영 fixture 쓰기가 필요하면 별도 범위 승인을 받는다.
4. 이 보고서와 증거를 같은 Drive 파일에서 갱신한다. 완료 후 임시 worktree/branch를 Git-aware 방식으로 정리한다.

현재 임시 worktree 두 개는 배포 승인 대기·정확한 후보 및 증거 보존이라는 활성 이유로 유지한다. 메인 작업 폴더의 기존 staged/untracked 변경과 로컬 전용 커밋은 건드리지 않았다.

## 복구

아직 실제 서비스는 이전 SHA를 실행 중이므로 사용자 데이터 복구는 필요하지 않다. 준비한 배포를 철회하려면 이번 source pin staged 변경만 검토·해제한다. 다른 설정이나 다른 작업의 staged 변경을 폐기하지 않는다.

신규 형식으로 편집한 노트가 생긴 뒤에는 이전 Markdown 편집기 프런트엔드로 무조건 rollback하지 않는다. 기존 본문은 Markdown으로 읽을 수 있어도 구형 편집기로 저장하면 계층 주석이 제거될 수 있으므로 호환되는 roll-forward 수정을 우선한다. 최신 사용자 내용을 덮어쓰는 DB rollback은 하지 않는다.
